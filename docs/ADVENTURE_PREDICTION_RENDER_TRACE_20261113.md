# 방향 전환 예측·렌더링 추적

기준 `6a4d756c`. 격리 Vite 플러그인으로 예측 설정, React 렌더 및 Canvas 목표 변경을 계측했다. 로컬 Chromium 390×844, 대체 이미지, 요청당 600ms의 모의 API 지연이며 실제 D1·물리 기기는 사용하지 않았다. 첫 입력 직전부터의 한 사례:

- 412ms에 (7,8) 예측을 설정하고 React가 받았다.
- 417ms 위쪽 입력으로 (7,7) 예측을 설정했고 React가 이를 받았다.
- 418ms 첫 관련 그리기에서 실제 표시 좌표는 약 (5.98,8), 이전 그리기 목표는 (6,8), 새 목표는 (7,7)이었다. 즉 (7,8)은 React에 전달됐지만 필드의 그리기 목표가 되기 전에 다음 예측으로 교체됐다.
- 512ms 버퍼가 같은 (7,7)을 다시 내보냈고 612ms에 (7,6)을 내보냈다. 첫 요청 응답은 622ms였다.

다른 사례에서는 (7,8)이 그리기 목표가 된 직후 아직 보간 중인 상태에서 (7,7)이 도착했다. 두 경우 모두 실제 그리기 위치와 새 목표 간 대각선 거리가 기존 큰 보정 기준을 넘어 즉시 이동했다. 중간점은 예측 생성이나 React 상태 설정 이전에 사라진 것이 아니라, 그리기 주기에서 최신 목표만 사용하거나 이전 목표가 아직 완료되지 않아 표시 경로로 이어지지 않았다.

로컬 후보는 같은 리비전의 인접한 직전 예측만 시각 경유점으로 전달해 경로를 보간하고, 서버 교정에는 적용하지 않았다. 위상별 세 모의 실행에서 회전 직후 빨간 픽셀은 기존의 한 프레임 대각선 이동 대신 수평 뒤 수직으로 움직였다. 그러나 서버 응답 후 후속 예측이 같은 프레임에 전달될 때 경유점 정보가 없어 남은 한 칸이 즉시 건너뛰는 사례가 재현됐다(예: y 229→195). 타이밍과 안전성의 완전한 전후 비교를 통과하지 못해 후보 코드를 제거했다. 예측 경로의 확인된 접두부와 그리기 큐를 구분하고, 서버 응답·충돌·조우·타임아웃에서 폐기할 기준을 설계해야 한다. 화면용 중간점은 실제 서버 이동으로 재전송해서는 안 된다.
