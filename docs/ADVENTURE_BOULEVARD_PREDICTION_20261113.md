# 북쪽·남쪽 대로의 이동 예측

`Lagsol.md`의 네 칸 후속 예측 제한을 현재 코드와 대조했다. 북쪽·남쪽 대로의 평지에서 최초 요청을 기다릴 때 표시 가능한 경로는 최초 한 칸과 후속 네 칸뿐이었다. 두 대로에는 긴 포장길이 있으며, 서버는 각 칸을 순서대로 검사해 전환이나 충돌에서 멈춘다. 두 대로의 `.`·`,` 평지에만 기존 최대 12칸 버퍼를 적용한다. 상호작용 표식, 구역 출입, 위험 예측, 실내와 그룹 상태에서는 기존 제한을 유지한다. 서버 요청·리비전·저장·이동 속도는 바꾸지 않는다.

모의 API가 첫 응답을 1,120ms 동안 보류한 Chromium 검사에서 각 대로의 접근성 위치는 시작점 x=2에서 기존 x=7, 변경 후 x=14까지 표시됐다. 서버 응답 전 실제 위치는 바뀌지 않았고 승인 후 순서대로 일치했다. 응답을 거절하면 최초 위치로 돌아갔다. 위험 플래그가 있는 경우 기존 x=7 제한을 확인했다.

별도 북쪽 대로 Canvas 추적에서 최초 응답을 1,200ms 지연하고 동일하게 약 800ms 직진 입력을 유지했을 때 이전 코드는 다섯 칸(마지막 목표 414ms), 변경 코드는 아홉 칸(마지막 목표 831ms)을 순서대로 그렸다. 두 실행 모두 그린 경로와 요청 순서·서버 최종 위치가 같고 동시에 보낸 이동 요청은 한 개였다. 이는 모의 네트워크와 대체 이미지의 예이며 실제 운영 RTT, 실제 기기 프레임 시간 또는 구역 전체의 지연을 뜻하지 않는다.

격리 SQLite API에서 두 대로의 12칸 이동, 128보 친밀도, 재화와 구형 위치, 오래된 리비전 거부 및 출구에서의 부분 처리·재접속을 확인했다. 단위 검사로 그룹·위험·출입 경계의 제한을 확인했다. 실제 Sites 병합본·운영 D1·실제 기기와 두 탭 경합은 이 변경으로 검증하지 않았다. `testfailed.md`의 기존 복구 실패 기록도 유지한다.
