## 추가 진단 수정과 검증

GET 실패 경로의 원시 오류/stack 노출을 합성 시험 문자열로 재현하고, 단계·요청번호·표준 오류 종류만 남기도록 바꿨다. 클라이언트는 허용된 오류 code와 UUID만 보존하고 표시하며 복구 GET까지 실패해도 최초 POST의 오류 번호를 유지한다. 원시 메시지를 남기지 않는 서버 진단과, 기존 게임 규칙 메시지를 사용자에게 보여주는 ACTION_FAILED 응답은 구분한다. 자세한 경계는 `API_FAILURE_DIAGNOSTICS_QA_20261105.md` 후속 절 참조.

실제 전투 API의 동시 같은 revision 요청은 한 건200과 한 건REVISION_CONFLICT409가 되었고 한 번만 저장됐다. 대사가 남은 동안 기술을 쓰는 요청은 ACTION_FAILED409와 저장 불변, 대사 확인 후에는200이었다. 이는 구분 가능한 두 재현 사례이며 운영 신고 원인이 어느 쪽인지 입증하지 않는다.

최종 코드의 일반 전체 **820/820**(150.7초), Worker 정책의 변경 API/응답 집중 **17/17**(1.3초), 타입·production 빌드 통과. 이번 후속에서 Worker 전체를 다시 실행했다고 보고하지 않는다. 앞선73b13c3의 Worker 전체814/814는 이전 묶음의 근거다. 실제 모바일/PC 오류 복구4/4에서 최초 POST 번호·저장 보존, POST1회/GET1회·자동 POST 재전송0·가로 넘침0을 확인했다.

## 실제 이미지 PC 계측에서 좁힌 범위

실제 GIF8개의 로컬 사본과 같은 합성 전투를 개발24경로, 최적화 번들24경로, 관찰자 비용을 줄인4경로에서 비교했다. 정상 CPU의 최적화된 싱글/더블 세 턴에는50ms 이상 긴 작업이 없었다. 입력 제출 후 다음 입력까지 싱글 약1.30초, 더블 약2.59~2.84초가 걸렸으며 순차 전투 이벤트 재생을 포함한다. 이는 모든 실제 PC/네트워크에서 끊김이 없다는 증거가 아니다.

CPU4배 제한의 최적화 더블에서 기록된 일부 긴 작업은 추가 단일 CPU 추적으로 **최종 POST 제출 전 기술 메뉴 선택 구간**으로 좁혀졌다. 단일 추적의 긴 작업4개는91/72/62/54ms였고, 제출 후 전투 재생 구간은0개였다. Playwright의 클릭 대상 확인·hit-test 비용도 섞여 있다. React/로그 스크롤 함수의 전체 구간 누적 비용을 하나의 긴 작업 원인으로 해석하지 않는다. CPU 샘플링 자체가 부하를 추가하므로 이 추적 시간을 앞선 계측과 직접 비교하지 않는다.

성능 제품 코드는 추정으로 수정하지 않았다. 실제 운영PC의 심한 끊김과 동일한 원인이라는 근거는 아직 없다. 운영 프로필에는 실제 이미지/CDN 지연, GPU·장치·브라우저 조건, 메뉴 선택부터 제출/재생까지의 프레임 기록이 필요하다. 이 작업의 프로파일러·계측 API는 격리 테스트 서버에만 있고 운영 앱에 추가하지 않았다.

근거: `.sites-runtime/tests/ui-readability/performance*/summary.json`, `performance-production-cpu/cpu-summary.json`과 `warm-turn.cpuprofile`. 원본 저장·헤더·토큰을 포함하지 않는 합성 계측이다. 자세한 재현 절차와 최종 lint는 [브라우저 계측 QA](PC_REAL_ARTWORK_PERFORMANCE_QA_20261105.md)를 따른다. 이번에 실행한 격리 브라우저 서버는 종료했다.
