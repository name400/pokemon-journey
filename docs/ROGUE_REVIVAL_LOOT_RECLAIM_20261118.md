# Trainer Revival Blessing and pickup loot

The pinned source explicitly removes all pending post-battle loot entries belonging to a trainer Pokémon when that Pokémon is successfully revived by Revival Blessing: https://github.com/pagefaultgames/pokerogue/blob/7c0881255af5cd51992e513ff93c2f71adbe40e0/src/data/moves/move.ts#L7169. Its held items remain on the Pokémon; a later faint can create new loot entries.

The local engine recorded each faint but did not reclaim those entries on enemy revival. An isolated real trainer battle confirmed that a held modifier became two pickup candidates after one Pokémon fainted, was revived and fainted again. For new runs, `revivalLootReclaimRule: source-v1` removes only entries for the successfully revived enemy immediately after the native revival action. Failed revival, player revival, other Pokémon's entries, held items and older runs remain unchanged. The flag is persisted with combat; no historical save migration is attempted.

A real battle with save codec between turns checked revival, a second faint, battle victory and Pickup, for new and legacy runs. Tests also checked distinct unrelated ledger entries, a native item and a modifier, failed enemy revival, player revival and a separate saved object. Existing Pickup, Revival Blessing and Last Respects regressions ran sequentially: 20 tests passed (two files are reported as aggregate tests by node). Other double-battle reward combinations, concurrent API requests, every item-transfer/revival combination, source runtime, browser and devices are not validated. No existing server or production data was used; Sites was not deployed.

Follow-up double-battle boundary: an isolated real player turn was used with an initially fainted enemy reserve and synthetic pre-populated loot records. The trainer revived that reserve, removed its record under the new flag and kept an unrelated record; legacy rules retained both. State and an unrelated object survived codec restore. Pickup, Revival Blessing and Last Respects suites were rerun: 21 tests passed, with two files reported as aggregate tests. The ledger was seeded for this particular double case.

Natural double-battle follow-up: a separate real turn knocked out an item holder and the trainer revived it later in the same turn; no ledger entries were injected. A second scenario continued through re-faint, victory and two Pickup owners, round-tripping the save between turns: the new rule yielded one item and the legacy rule two. The source item remained held during revival. Related sequential suites passed 23 tests, including two aggregate test files. Other item and ability combinations, actual source runtime and browser/device behavior remain unverified.
