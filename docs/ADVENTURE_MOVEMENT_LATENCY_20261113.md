# 이동 지연 재측정

기준 `cc0217c8`. 로컬 Chromium 390×844와 Vite 테스트 화면에서 게임 코드를 실행하고 `/api/world`를 메모리 모의 서버로 대체했다. 이미지 요청도 대체했으며, 각 이동 요청의 처리 전 150ms 또는 600ms를 기다렸다. 오른쪽을 약 400ms 누른 뒤 계속 직진하거나 위쪽으로 전환해 약 400ms 유지했다. 아래 수치는 각 조건 두 번의 탐색 실행이다. 위치는 캔버스 `aria-label`의 논리 좌표 변경 시각이므로 실제 픽셀 보간·물리 화면 지연이 아니다.

| 요청 지연 | 입력 | 첫 위치 반응 | 일반적인 위치 간격 | 방향 전환 직후 간격 |
| --- | --- | --- | --- | --- |
| 150ms | 직진 | 8–10ms | 약 99–120ms; 한 실행 마지막 184ms | 해당 없음 |
| 150ms | 전환 | 6–10ms | 약 94–112ms | 약 100ms |
| 600ms | 직진 | 7ms | 약 98–105ms | 해당 없음 |
| 600ms | 전환 | 6–7ms | 약 99–105ms | 약 100ms 또는 190ms |

이후 저장된 재현 스크립트 실행에서도 150ms와 600ms 전환 각각 한 번씩 약 189–199ms 간격이 관찰됐다. 방향 입력 시 이미 예측해 표시한 첫 칸을 주기 타이머가 나중에 버퍼에 편입하는 순서와 관련될 가능성이 있으나 이 계측만으로 원인을 확정할 수 없다. 방향 변경이 주기 경계에 걸치는지, 실제 캔버스 그리기와 요청 응답이 어떤 순서인지 브라우저 프레임·입력·ACK를 함께 추적해야 한다. `Lagsol.md`의 예전 방향 전환 설명과 달리 현재 타이머는 요청을 넘어 유지되며 대기 중 새 방향도 버퍼에 넣는다.

모든 측정에서 요청은 직렬 처리됐고 최종 화면·서버 좌표가 일치했다. 추가 브라우저 회귀는 대기 중 방향 전환을 서버 경로와 비교했고, 예측·충돌 단위 검사도 통과했다. 모의 API에는 실제 저장소가 없으므로 이 결과만으로 D1 저장, 여러 탭이나 운영 네트워크의 성능을 보증할 수 없다. 게임 동작을 변경하지 않았으며 전후 성능 개선을 주장하지 않는다. 알려진 복구 펜스 경합은 `testfailed.md`에 유지한다.

재현: `tests/browser/ui-readability`의 Vite 설정으로 포트 5222를 열고 `PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs node tests/browser/ui-readability/cloud-movement-latency.mjs`를 실행한다. 다른 포트는 `UI_TEST_URL`로 지정한다.
