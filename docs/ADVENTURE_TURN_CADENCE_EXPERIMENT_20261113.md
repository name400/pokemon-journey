# 방향 전환 대기 실험

`8ca589a5`의 모의 API·Chromium에서 입력과 예측 및 Canvas 목표를 함께 기록했다. 오른쪽으로 이동하다 위쪽으로 전환할 때, 입력 순간 보여 준 회전 칸을 다음 주기에 버퍼로 옮기는 동안 새 칸이 추가되지 않는 경우를 확인했다. 600ms 모의 응답의 비교 실행에서 회전 직후 두 Canvas 목표 간격은 기존 138ms였다. 이 값은 실제 화면의 좌표 변화 전체가 아닌 Canvas 목표 갱신 시각이다.

이미 표시한 회전 칸이 버퍼에 들어갈 때 다음 칸까지 미리 처리하는 후보를 시험했다. 타이머 직전에 누른 키가 한두 밀리초 만에 두 칸으로 늘어나는 위험을 막기 위해 키가 계속 눌려 있고 표시 좌표·리비전이 일치하며 입력 이후 기본 주기에서 한 프레임(17ms)을 뺀 시간이 지났을 때만 적용했다. 600ms 모의 응답에서 세 실행의 회전 직후 Canvas 목표 간격은 100ms, 115ms, 138ms였고, 같은 400ms 회전 유지 입력에 9~10칸이 표시·저장됐다. 이전 실행은 9칸이었다. 각각의 모의 검사는 실제 전송 경로와 Canvas 목표 및 서버 최종 좌표가 일치했고 요청은 동시에 하나였다.

후보의 효과가 실행별로 일정하지 않고 재현된 이득이 타이밍 잡음보다 충분히 크다고 판단하기 어려워 게임 코드에는 적용하지 않았다. 서버 모의 지연과 캔버스 목표만 측정했으며 실제 휴대폰·운영 D1·네트워크 및 화면에 보이는 픽셀의 지연을 측정하지 않았다. 원인으로 특정한 타이머 중복 소비는 실제 운영의 주된 병목으로 확정되지 않았다.

후보 상태에서 키보드·포인터·회전·키 해제·충돌·부분 이동, 조우 중 전환, 중복 응답과 timeout 펜스 경합의 모의 검사를 실행했다. 복구 검사는 첫 실행에서 초기 Canvas 표시를 기다리다 시간 초과했고 별도 재실행은 통과했으나 최초 실패 원인은 미확정이다. 상세는 `testfailed.md`에 남긴다. 후보 폐기 후 기존 예측 단위 검사는 통과했다. 실제 두 탭·실패 대상 Sites 병합본에 대한 기존 미검증 기록은 그대로 유지한다.

다음 조사에서는 입력 시각에 맞춰 다음 표시 주기를 조정하는 방식과 키 해제·충돌·조우 시 대기 콜백 취소를 별도 설계하고, 같은 입력 시각을 고정한 전후 프레임·보행 수·서버 경로를 비교해야 한다. 4칸 제한과 운영 네트워크·서버 응답 비용도 별도로 측정해야 한다.
