# 이동 복구와 새로고침 경합 — 2026-11-12

`d894e0a`에서 저장소를 차단한 브라우저가 이동 요청을 기다리는 동안 타임아웃 복구 펜스를 보낸 뒤, 그 응답을 받기 전에 같은 탭을 새로고침하는 순서를 재현했다. 초기 진입 펜스, 이전 페이지의 타임아웃 펜스, 새 페이지의 진입 펜스가 차례로 실행되어 revision이 1에서 4가 된다. 이는 같은 이동을 세 번 저장한 것이 아니다. 원래 이동 요청을 마지막에 풀면 이전 revision으로 저장을 시도해 409로 거절되고, 새 페이지와 서버가 같은 위치를 유지하며 다음 입력은 성공한다. `cloud-movement-timeout-race.mjs`의 `pending-fence-reload`가 이 순서를 고정한다.

서버는 같은 계정의 모든 탭에서 하나의 revision을 사용한다. 따라서 다른 탭이 펜스 전 revision으로 진행하던 이동 또는 저장은 409로 거절될 수 있다. 서버 저장이 이미 이뤄진 작업은 롤백하지 않지만, 거절된 입력은 재동기화 후 다시 입력해야 할 수 있다. 이는 저장을 보호하는 대신 다른 탭의 진행을 중단시킬 수 있는 영향이며, 두 실제 브라우저 탭과 운영 환경에서의 전체 사용자 경험은 아직 검증하지 않았다.

기존 페이지의 펜스가 이미 서버에 도착했을 수 있어 요청 취소만으로 중복 실행을 방지할 수 없다. 새 페이지가 조건 없이 첫 펜스를 생략하면 기존 요청이 복구 조회 후 저장되는 원래 오류가 돌아온다. 저장소가 차단된 상황에서도 안전하게 요청을 식별하는 방법과 두 탭의 동시 작업을 별도로 설계·검증하기 전까지 중복 펜스를 제거하지 않는다.


## 저장 전 충돌의 복구

서버가 이동·방향 전환 요청을 리비전 사전 검사에서 거절한 경우에만 `MOVEMENT_PRECHECK_CONFLICT`를 반환한다. 이 응답은 해당 이동이 저장되지 않았음을 뜻하므로 클라이언트는 추가 펜스 없이 최신 상태를 조회한다. 그 외 409나 시간 초과는 저장 여부가 불명확하므로 기존 펜스를 유지한다. 두 탭 모의 API 재현에서는 총 펜스가 5회에서 4회로 줄고 다음 이동은 한 번 저장됐다. 최초 진입·새로고침 펜스에 의한 다른 탭 이동 거절과 저장소 차단 새로고침의 세 펜스는 해결되지 않았다. 운영 D1과 실제 사용자 환경은 검증하지 않았다.


## 새로고침 시 기존 페이지 복구의 시작

브라우저 모의 시험에서 새로고침으로 기존 이동 요청이 중단되면, 기존 페이지가 사라지기 전에 오류 처리를 시작하여 해당 이동 리비전의 복구 펜스를 보낼 수 있다. 이후 새 페이지의 진입 펜스가 실행되면 초기 진입을 포함해 세 요청이 된다. 기존 페이지의 오류 처리가 시작되지 않으면 두 요청이다. 두 순서를 각각 확인한 결과 지연된 기존 이동은 거절되고 위치와 이동 횟수는 일치했으며 다음 이동이 한 번 저장됐다. 테스트는 각 요청의 리비전과 파트너, 저장 리비전, 이동 횟수를 검사한다. 다만 기존 페이지의 펜스가 이미 서버에 도착했는지 새 페이지에서 알 수 없으므로 단순 생략은 적용하지 않았다. 실제 운영 D1, 브라우저별 탐색 취소 및 두 탭의 동시 작업에 대한 영향은 추가 검증이 필요하다.
