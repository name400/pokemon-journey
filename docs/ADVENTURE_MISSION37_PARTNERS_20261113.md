# 미션 37 방어 작전 동료 파티

원작의 [Ivor](https://bulbapedia.bulbagarden.net/wiki/Ivor), [Canari](https://bulbapedia.bulbagarden.net/wiki/Canari), [Lebanne](https://bulbapedia.bulbagarden.net/wiki/Lebanne), [Corbeau](https://bulbapedia.bulbagarden.net/wiki/Corbeau), [Griselle](https://bulbapedia.bulbagarden.net/wiki/Griselle)의 미션 37 동료 전투 자료에 따라 방어 작전 다섯 구간의 선두·후속 포켓몬, 레벨, 기술, 성별과 지닌 도구를 연결했다. 동료가 쓰러지면 기존 다수 턴제 엔진이 동료의 다음 포켓몬으로 교체한다. 동료 포켓몬과 도구는 플레이어 보유함이나 가방에 추가되지 않는다.

현재 전투 엔진은 플레이어 외 동료 측이 하나이므로 Ivor와 함께 현장에 있는 Gwynn, Griselle과 함께 현장에 있는 Grisham의 독립된 동시 전투는 재현하지 않는다. 메가스톤을 지니지만 동료 AI의 자동 메가진화와 플러스 기술은 구현하지 않았으며, 실시간 전투와 원작의 기술 선택 방식도 턴제 각색이다. 미션 36의 Lida·Naveen 임시 파티는 이번 변경 대상이 아니다.

새로 시작하는 각 방어전에서만 새 파티를 만들고 이미 진행 중인 전투 스냅샷과 플레이어 파티·진행 저장은 변환하지 않는다. 다섯 구간의 구성·진행·재조회와 이전 동료 전투 복원을 격리 API로 검사했다. 원작 실기와 운영 환경은 검증하지 않았다.

## 동료 자동 메가진화

위 다섯 동료와 새로 시작한 방어전에는 동료의 첫 유효 행동에서 메가진화할 수 있으면 함께 선택하도록 연결했다. 각 동료의 원작 메가스톤을 사용하며 동료가 별도의 플레이어 파티나 가방을 차지하지 않는다. 메가진화는 시뮬레이터의 합법 행동을 따르고 동료의 선택은 플레이어의 메가진화 선택과 독립적이다. 이미 저장된 진행 중 배틀과 다른 동료 배틀은 자동 메가진화 규칙을 추가하지 않는다.

다섯 종의 실제 변신, 플레이어와 같은 턴에 각자 변신, 저장 복원, 기존 스냅샷, 플레이어 소유권과 동료 교체를 격리 엔진·API 검사했다. 플러스 기술, 두 번째 동료의 별도 동시 참전과 원작의 실시간 전투는 여전히 미구현이다. 위 본문의 자동 메가진화 미구현 서술은 이 절로 갱신한다.

## 미션 36 첫 방어전 동료

[센트리코 광장 동료 자료](https://www.serebii.net/pokearth/lumiosecity/centricoplaza.shtml)에서 미션 36 Lida와 Naveen의 레벨·기술·메가스톤을 확인했다. 새 첫 방어전의 동료 쪽에 각자의 선두 아쿠스타·곤율거니와 후속 블로스터·아리아도스·배바닐라·깜까미를 연결했다. 아쿠스타가 행동할 수 있으면 메가진화한다. 동료들은 플레이어 파티나 보유함에 들어가지 않는다.

현재 엔진은 동료 한 팀에 최대 여섯 마리와 메가진화 한 번만 허용하므로 두 인물의 원래 네 마리씩 총 여덟 마리 중 각각 세 마리만 한 팀에 담은 턴제 절충안이다. 에몽가·악비아르는 빠져 있고 두 사람이 독립적으로 동시에 행동하거나 각자 메가진화하지 않는다. 기술플러스와 원작의 실시간 전투도 구현하지 않았다. 이전에 시작된 배틀 스냅샷은 변경하지 않는다. 격리 API의 미션 진행·기권·패배·재도전과 단위 전투의 메가진화·소유권을 검사했으며 운영·원작 기기는 미검증이다. 이 절이 위의 미션 36 임시 파티 제외 서술을 갱신한다.

## 두 번째 동료 준비 — 전투 미연결

[Gwynn](https://bulbapedia.bulbagarden.net/wiki/Gwynn)과 [Grisham](https://bulbapedia.bulbagarden.net/wiki/Grisham)의 미션 37 파티를 기존 첫 동료와 별도 소유 식별자를 갖는 데이터로 준비했다. Gwynn의 펌킨인은 작은 크기 폼이다. 데이터의 종·레벨·기술·도구와 직렬화는 단위 검사했지만, **두 번째 동료의 전투 행동과 게임 연결은 아직 구현되지 않았다.** 기존 두 진영 대 다수 전투는 네 개의 시뮬레이터 측을 사용하므로 두 번째 독립 동료를 그대로 추가할 수 없다. 별도 형식에서 세 아군의 동시 행동과 파티별 교체·메가진화, 사용자 소유 포켓몬 구분, 전투 승패·중간 저장·기존 스냅샷 및 화면 슬롯을 함께 구현하고 검증해야 한다. 이번 데이터 준비는 기존 진행 또는 실행 중인 전투를 변경하지 않는다.

후속 실험으로 별도의 세 자리 시뮬레이터 스냅샷 생성·복원 코드를 추가했다. 실제 플레이 경로에 연결되지 않은 프로토타입이며, 플레이어 6마리와 각 동료 전체 파티를 중복 없이 보존하면서 세 선두의 한 턴 행동과 직렬화 후 재복원을 격리 시험했다. 시뮬레이터 내부에서는 세 소유자의 포켓몬이 같은 편에 있으므로, 소유자별 교체 제한·자동 선택, 개별 메가진화, 전투 종료와 보상, 연출 슬롯 및 API 재접속 처리가 완성되기 전에는 실전에 사용하면 안 된다. 기존 네 진영 전투와 구형 저장에는 적용하지 않는다.

후속 프로토타입에 두 동료의 자동 기술 선택과 소유자별 교체, 전투 종료 판정을 추가했다. 동료의 파티가 전멸하면 다른 동료의 예비 포켓몬을 대신 사용하지 않고 빈 자리를 유지하는 사례와 승리 후 스냅샷 복원을 격리 시험했다. 이는 위 문단의 미구현 목록 중 실험 엔진 부분만 진전된 것이며 실제 미션 API·화면·보상, 개별 메가진화, 모든 전투 상황의 검증은 여전히 남아 있다. 기술 선택은 원작 AI를 재현한 것이 아니다.

세 자리 활성 포켓몬·대상·플레이어 교체 목록을 조회하는 실험 응답과, 공유 시뮬레이터 편에서 플레이어 소유 포켓몬만 추출하는 함수를 추가했다. 저장·재접속 후 소유권과 대상 슬롯을 단위 검증했다. 기존 공통 전투 종료 처리는 시뮬레이터 한 편을 통째로 플레이어 보유함에 동기화하므로 이 형식을 그대로 넣으면 동료 포켓몬이 저장될 위험이 있다. 따라서 아직 API에 활성화하지 않았고, 전투 결과·경험치·보상·중복 요청 처리와 세 자리 화면 및 연출을 함께 연결하고 검증해야 한다.

후속 변경으로 내부 실험 플래그 `zaMission37TripleV1`이 명시된 저장에서만 2·6구간의 실제 API 생성·행동·재조회·승패·경험치와 진행 처리를 연결했다. 저장 동기화는 플레이어 소유 ID만 허용한다. 격리 SQLite API에서 재조회, 승리, 패배, 기권·재도전과 오래된 리비전 재요청을 검사했으며 동료가 보유함에 추가되지 않았다. 이전 저장과 진행 중인 네 진영 전투는 그대로 유지한다. **일반 게임 진행에서는 이 플래그를 설정하지 않으므로 아직 새 전투를 플레이할 수 없다.** 세 자리 화면·연출, 도구, 메가진화, 플레이어 전멸 후 이어가기와 실제 D1·브라우저 검증이 남아 있으며 활성화 전에 해결해야 한다. 기존 공통 완료 처리에 그대로 넣는 위험은 이 전용 경로에서 피했다.

실험 화면에 양측 세 자리의 위치·체력과 기술·피해·교체 이벤트를 연결하고, 동료만 행동해야 할 때 계속하기 요청을 제공했다. 광역기의 세 대상과 이전 HP 및 교체 전 슬롯을 격리 시험했다. PC·모바일 Chromium에서 대체 이미지를 사용한 화면 배치를 확인했으며 실제 이미지·실제 D1과 전체 브라우저 전투는 검증하지 않았다. 일반 플레이 활성화는 여전히 보류하며 도구·메가진화와 동료만 남은 장시간 전투 및 재접속 검증이 남아 있다.

실험 경로에 회복 도구·기력의조각·기력의덩어리와 소유자별 메가진화를 추가했다. 공유 시뮬레이터의 편당 1회 제한을 이 실험 배틀에 한해 소유자별로 분리하며, 사용 여부는 스냅샷과 함께 저장한다. 세 소유자의 같은 턴 변신·복원, 소유권과 도구 차감·재요청 거부를 격리 검사했다. 플레이어 전멸 후 동료 전투는 요청당 한 턴씩 저장하며 130턴과 중간 JSON 복원을 시험해 128턴 초과에도 이전 진행이 사라지지 않았다. 실제 D1·브라우저 전체 흐름과 다른 특수 변화는 미검증이며 일반 플레이 플래그는 계속 비활성이다.

실제 세 자리 전투 엔진과 모의 API를 연결한 Chromium 검사에서 PC·모바일의 공격 1회와 새로고침 후 HP·다음 행동·중복 요청 방지를 확인했다. 그림은 모의 응답이다. 공식 Miniflare 로컬 D1의 `getD1Database('DB')`는 프로세스가 시작된 뒤 2분 가까이 응답이 없어 종료했으며 오류 메시지는 출력되지 않았다. 따라서 실제 D1의 해당 API 및 브라우저 전체 승패·재접속 검사는 완료되지 않았고 일반 플레이는 활성화하지 않았다.

추가 진단에서 Miniflare Worker의 준비와 일반 요청은 정상이며, Node 바인딩 프록시를 얻는 호출만 멈췄다. `cf:false`는 기본 위치 정보 조회만 끄는 공식 설정으로, 이 설정과 Worker 내부의 D1 바인딩을 이용하자 격리 로컬 D1이 정상 응답했다. 실제 게임 API 코드를 Node에서 실행하고 테스트 전용 Worker를 통해 D1에 연결한 검사에서 미션 37 승리·기권·재도전·재조회, 오래된 요청 거절과 보유함 소유권을 확인했다. 이 검사는 실제 게임 Worker 안에서 실행한 경로나 운영 D1을 검증한 것이 아니다. 브라우저 전체 승패 흐름 또한 아직 모의 API이며 일반 플레이 플래그는 보류한다.

이후 게임 API를 테스트 인증만 대체해 격리 Miniflare Worker에 직접 묶어 실행하고, 그 Worker의 로컬 D1으로 승리·기권·재도전·동료만 남은 전투의 이어가기·복원·이전 리비전 거절 및 소유권을 검사했다. PC·모바일 Chromium에서도 이 Worker와 D1에 연결해 진입·한 턴 후 새로고침·승리·저장 복원을 검사했다. 브라우저 검사에서 결정적인 승리를 위해 적 팀과 HP를 격리 테스트 데이터로 조정했고 외부 이미지는 모의 처리했다. 운영 D1·실기기·자연 진행 전체 및 브라우저에서의 패배·도구·각 동료 메가진화 검증은 아직 하지 않았으며 일반 플레이 플래그는 보류한다.
