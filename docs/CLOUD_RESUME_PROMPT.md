### 수수께끼 상자와 챌린지 출전 제한

실제 이벤트 액션에서 금지된 고속 개체가 경주를 잘못 이기게 하지 않는 상황, 출전 가능한 개체의 승리·열매 지급, 저장 복구 뒤 화난 상대와 전투·포획 및 다른 슬롯 보존을 검사했다. 확인 불가능한 폼 기록에서는 전체 문서가 변경되지 않는 것도 확인했다. 자연 추첨에서 허용 생존자가 두 마리일 때 The Strong Stuff가 제외되고 세 마리일 때 출현 가능한지 검사했다. 원본 폼 전체나 다른 이벤트 전수 대조, 실제 계정 플레이는 하지 않았다. 미스터리 이벤트와 전투 규칙 및 미지원 특수 폼의 나머지는 계속 구현해야 하며 운영 배포는 하지 않았다.
추가 격리 검사에서는 챌린지에서 자연 출현한 The Strong Stuff를 선택·저장 복구해 실제 전투에 진입했고, 상대의 방어·특수방어 강화가 재복원 뒤 유지됨을 확인했다.

### 희귀 품종의 매료 참가자 추첨과 훔치기 참가 조건

원본도 적격 후보에서 균등 추첨하지만, 원본은 요구 조건·화면을 다시 평가할 때 재추첨할 수 있으며 Phaser 난수 상태를 사용한다. 이번 구현은 기존 데이터 보호를 위해 이벤트에서 한 번 정해 저장하고 프로젝트의 `classicRandom`을 사용하므로 원본의 전체 시드·추첨 시점·난수 순서와 동일하지 않다. 원본 세이브나 시드의 완전 호환을 뜻하지 않는다.

Fight or Flight 및 Slumbering Snorlax의 훔치기 선택도 원본의 `MoveRequirement(..., true)`에 맞춰 챌린지 출전이 가능한 생존자만 후보로 표시·허용한다. 금지된 개체가 먼저 있어도 허용된 개체를 선택하고, 저장 복구 후 보상과 다른 슬롯 보존을 검사했다. 두 이벤트는 적격 후보가 여러 명일 때 기존처럼 첫 후보를 쓰며, 원본의 후보 무작위 추첨은 아직 남아 있다. 다른 이벤트·전투 규칙과 미지원 특수 폼은 계속 대조해야 하고, 실제 계정 전체 플레이와 운영 배포는 하지 않았다.
원본 `randSeedInt`는 후보가 0명 또는 1명이면 난수를 소비하지 않는다. 구현 중 한 명인 경우에도 소비하던 초기 처리와 검사를 이 원본 경계에 맞춰 수정했고, 두 명 이상일 때만 프로젝트 난수 한 값을 사용한다. 이 수정 뒤 전체 회귀를 다시 실행했다.

### 두 훔치기 이벤트의 후보 추첨

### 바다 안내·화산 후보와 챌린지 피해

원본의 바다 기술 조건은 선택지 활성 검사에서 출전 가능자를 쓰지만 후보 조회에서는 전달된 전체 파티를 다시 살핀다. 화산의 타입·특성 조합도 활성 검사와 후보 조회가 다르며 불꽃 타입 조회는 기절 여부를 자체 필터링하지 않는다. 따라서 기절·챌린지 금지·미검증 폼·융합 등이 섞여 원본 후보 범위가 복잡한 경우에는 새 추첨을 강제하지 않고 기존 흐름을 보존한다. 해당 예외는 원본 후보 추첨과 일치한다고 검증한 것이 아니다. 프로젝트 `classicRandom`과 원본 Phaser 상태·요구 조건 재평가 순서도 다르다.
