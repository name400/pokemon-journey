# 재접속 연출 확인 장부의 격리 설계

현재 전투 데이터의 이벤트 배열은 `output` 이후 포획 이벤트가 앞에 추가되기도 한다. 완료 여부의 키로 턴 번호나 배열 위치만 쓰면 다른 사건과 혼동할 수 있다. 이벤트 목록을 최종 확정한 후 새 무작위 배치 ID와 그 안의 각 이벤트 ID를 함께 저장하고, 저장된 배치의 ID는 재조회 때 바꾸지 않아야 한다. 구형 저장은 ID가 없으므로 미확인으로 취급한다. 서로 다른 배치의 동일한 이벤트 내용도 별개다.

`rogue-presentation-ledger.mjs`는 이 방식의 독립 자료 구조와 **사용자가 명시적으로 확인한** 이벤트 기록의 순수 함수를 제공한다. 동일 요청은 중복 항목을 만들지 않고 다른 뷰어 기록을 합치지 않으며 미선택 이벤트는 확인하지 않는다. 확정 배치와 장부를 호출자가 저장해야 하며 이 모듈은 저장·전투·재생·네트워크에 연결하지 않는다. 기존 저장은 변경하지 않는다.

실제 연동 전에는 이벤트가 추가·교체되는 모든 경로에서 배치를 최종 확정하고 서버 저장과 원자적으로 묶어야 한다. 서버는 클라이언트가 제출한 배치가 아닌 현재 저장된 배치와 대상 ID를 검증하고, 독립 확인 장부에 동시 쓰기 및 재시도 멱등성을 보장해야 한다. 기록 크기 제한·보존 기간도 미정이다. 저장 실패나 네트워크 장애 시 확인되지 않은 것으로 남겨야 하며, 기존 저장에는 자동으로 확인 기록을 만들어서는 안 된다.

특히 뷰어 ID의 복제 탭·브라우저 복원 시 독립성과, 불투명 가림 중 사용자에게 실제로 보였는지는 이 자료 구조만으로 보장할 수 없다. 시험용 서로 다른 ID는 실제 브라우저 탭 식별 검증이 아니다. 명시 확인 화면의 접근성·중단·서버 응답 손실·오래된 배치·동시 탭·구형 저장을 실제 API와 브라우저에서 검증하기 전에는 이 장부로 재생을 억제하지 않는다. 기존 재접속 반복은 미해결이다.

## 격리 API 단계

독립 POST 경로는 인증·동일 출처와 명시 확인을 요구하고, 클라이언트가 보낸 이벤트 내용이 아니라 인증된 사용자의 현재 저장에 이미 존재하는 배치를 읽어 최종 전투 이벤트와 비교한다. 저장 리비전이 달라지면 기록하지 않으며, 별도 테이블의 복합 키와 단일 조건부 SQL로 중복 요청 및 사용자별 2,048건 한도를 처리한다. 게임 저장 데이터·리비전은 변경하지 않는다. 격리 SQLite와 실제 라우트 함수에서 중복·다른 계정·구형 저장·수정된 이벤트·리비전 경쟁·한도와 원자적 실패를 검사했다.

전투 행동이 새 이벤트를 만든 경우 저장 직전에 최종 이벤트 목록의 배치 ID를 생성해 전투 저장과 함께 기록한다. 포획 이벤트처럼 엔진 출력 뒤에 추가된 이벤트도 확정된 순서로 포함한다. 재조회는 저장된 ID를 반환하며 구형 저장을 조회하거나 기존 슬롯을 선택할 때는 ID를 만들어 넣지 않는다. 기술 정리 등 이벤트가 바뀌지 않는 비연출 작업은 기존 ID를 유지한다. 격리 API의 실제 승리·더블 포획·연속 명령, 재조회, 중복 명령과 별도 확인 저장을 검사했다.

게임 화면은 아직 확인 API를 호출하지 않으며, 완료 기록으로 재생을 생략하지 않는다. 네트워크 응답 손실, 실제 D1 동시 요청, 뷰어 식별과 기록 수명·정리 정책은 미검증이며, 확인 API 성공도 실제 시청을 증명하지 않는다. 재접속 반복은 미해결이다.
